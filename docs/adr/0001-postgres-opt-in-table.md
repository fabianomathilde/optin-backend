# 0001 — Postgres schema for the opt-in table

- **Status:** Proposed (awaiting human review and acceptance)
- **Date:** 2026-11-19
- **Phase:** 2 (Postgres adapter)

## Context

Phase 2 replaces the in-memory adapter with a Postgres adapter managed by Flyway
(`src/main/resources/db/migration/`). We need the first table that stores opt-ins.

The domain (CLAUDE.md) requires an opt-in to have a validity date, a revocation (opt-out) state,
and at most one ACTIVE opt-in per (merchant, grantee). The initial column list was extended to
cover these rules.

## Decision

1. Table `opt_in`, created in `V1__create_opt_in_table.sql`.
2. Columns:

| Column        | Type                     | Nullable | Notes                                              |
|---------------|--------------------------|----------|----------------------------------------------------|
| `id`          | integer                  | no       | Primary key, default from sequence `opt_in_id_seq` |
| `merchant`    | varchar(14)              | no       | Merchant CNPJ. Format and check digits validated by the `Cnpj` value object in the domain |
| `grantee`     | varchar(14)              | no       | Financial institution receiving the opt-in         |
| `frequency`   | varchar(10)              | no       | `DAILY`, `WEEKLY` or `MONTHLY` (check constraint)  |
| `start_date`  | date                     | no       |                                                    |
| `valid_until` | date                     | yes      | Must be null or on/after `start_date` (check constraint). Matches the domain term `validUntil` |
| `status`      | varchar(10)              | no       | `ACTIVE` or `REVOKED` (check constraint)           |
| `revoked_at`  | timestamp with time zone | yes      | Must be set exactly when `status = 'REVOKED'` (check constraint) |

3. `id` is generated by the sequence `opt_in_id_seq` (`INTEGER`, owned by the `id` column). The
   application does not assign ids.
4. Partial unique index `uq_opt_in_active_pair` on `(merchant, grantee) WHERE status = 'ACTIVE'`.
   This is the database backstop for the "one ACTIVE opt-in per pair" invariant. Phase 2 maps a
   violation of this index to a domain error.
5. `frequency` uses `VARCHAR(10)` with a `CHECK` constraint. A Postgres `ENUM` was rejected (see Alternatives).
6. Column names use the domain terms `merchant`, `grantee` and `valid_until`. The table name `opt_in` was chosen by me.

## Alternatives considered

- **Postgres `ENUM` type for `frequency` and `status`.** Same values, but changing them needs
  `ALTER TYPE`. A `CHECK` constraint is simpler to evolve.
- **Lookup table for frequencies or statuses with foreign keys.** Overkill for fixed values.
- **`CHAR(14)` for documents.** The request specified `string(14)`, so `VARCHAR(14)` was used.
- **Application-assigned ids or identity column.** Rejected in favour of a sequence, as decided.
- **Column names `payee_document` / `financial_institution` / `end_date`.** Replaced by the domain terms.
- **`revoked_at` as a plain date.** Rejected: revocation is an event with a time, and the domain takes time from the `Clock` port.

## Consequences

- Revocation is a state change on the row (`status = 'REVOKED'`, `revoked_at` set). Rows are not deleted.
- The `ck_opt_in_revoked_at` constraint makes the row consistent: `revoked_at` is set if and only if the status is `REVOKED`.
- A revoked pair can be granted again by inserting a new row. The partial index allows this because
  only ACTIVE rows are constrained. The domain rule "a revoked opt-in cannot be reactivated" applies
  to the same row and must be enforced in the domain model.
- The `valid_until >= start_date` rule exists in both the domain (on grant) and the database.
- The sequence gives `INTEGER` ids, which cap at about 2.1 billion rows. Changing this later means a new migration.
- Flyway and the PostgreSQL driver are not yet in `pom.xml`, so this migration does not run until
  those dependencies and the datasource configuration are added.
- V1 was edited before it was applied anywhere, which is allowed. From now on, schema changes go in new migrations.
